# Blank-cell renderer defaults and rich input

Candidate 128/71 has a real healthy-input failure independent of the earlier worker fault. On a fresh, owned TEAM workbook, actual Manage worksheets → Add **Healthy Typed**, then a trusted mouse selection of A1, F2, keyboard typing **28** and Enter produced the same “Rich cell drawings or document formatting are not supported” save issue. The worker was not terminated. The visible cell retained 28 and the recovery copy retained the typed rich document. This is a failure record, not successful GUI edit/save qualification.

The pinned SDK's blank-cell editor assembles `renderConfig.background = { rgb: fill }` from that exact cell's document layout. With no fill, the live object has an undefined RGB member and JSON recovery spells it `{}`. Existing `attachWorkbookRichInput` already validates and removes editor-only document layout through the matching unit/sheet/row/column and active editor; its renderConfig checker accepted numeric fields but rejected this renderer color object. The stricter persistent rich-text reader correctly refused the remaining documentStyle.

The correction reuses that live adapter. It admits only the renderer background object with no fields other than RGB and with RGB exactly equal to the current matched editor layout's fill. It preserves every text run and the cell's existing style. Changed colors, extra background fields, authored margins, drawings and structured body content still refuse. No persistent reader or recovery schema was relaxed, and unsupported older documents are not silently migrated from JSON. New live edits can persist the already normalized documentStyle and retain that form through recovery serialization.
