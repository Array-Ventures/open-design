# Workbook calculation application barrier

The scalar result mutation is a notification: its pinned SDK handler is a no-op. The sheets plugin subsequently applies its values through asynchronous `SetRangeValues` mutations. Receiving a qualified result therefore does not prove that `book.save()` contains those results yet.

The calculation owner now keeps its existing deadline through those actual applications. Each expected application is bound to the already accepted calculation provenance, unit, sheet, exact value/type vector and source formula identities. Across RPC these objects are cloned, so correlation uses the existing canonical SHA helper; the local SDK path also retains the existing source-object provenance. Formatting fields are excluded because the SDK independently merges number-format styles. Only an accepted derived mutation whose actual resulting cells match can discharge its application. A late, mismatched or rejected application cannot complete the latest input epoch.

Membership waits require the applied replica acknowledgement, qualified scalar completion when formulas remain, and these real cache applications. The new quiescent wait additionally drains ordinary scalar work for clean History snapshot capture, with cancellation and failure owned by the existing worker deadline. Neither wait grants source/history authorization or promotes stored caches into calculated results.

A genuine regression against `13196db4` held the reverse cache mutation while allowing its scalar result: `awaitMembership()` resolved although the actual workbook cache was still not `#REF!`. The corrected production RPC suite passed all 14 cases; the existing formula display and worker-boundary suites passed 22 cases. An ordinary edit similarly proves quiescent completion returns the actual fresh value 40, rather than the prior cache 38. These are local source/RPC tests, not packaged runtime qualification or live worksheet-control enablement.

## Application integrity follow-up

A subsequent genuine regression against `0beb9a79` showed that a later public SDK listener could change an already admitted cache payload and incorrectly complete the wait. The local object fallback now recovers only calculation provenance, and recomputes the exact normalized vector both before and after application. A changed reverse-RPC vector is cleared before the SDK applies it. Mutation by a later listener after admission fails the owner immediately; no rollback of that already executed SDK mutation is claimed, and the failed result cannot complete the save gate or remain labeled calculated.

Normalization reuses the existing stored-cache preservation policy before promotion. This matters when a sheet contains both qualified formulas and unsupported/dependent formulas: its legitimate reverse-RPC vector must receive exactly the same source-owned stored-cache projection as the accepted scalar result. The normalization step alone never labels values calculated. All returned cell fields except the SDK-owned number-format style field `s` are bound, and the actual authored-input digest must remain unchanged after cache application. This is not a claim of security against arbitrary client JavaScript mutating native style resources.

The tests also cover an explicit epoch-stamped host calculation refreshing a genuine imported cache 999 to 38. This uses the supported host `SetFormulaCalculationStartMutation` path. The Node SDK facade's separate generic auto-trigger service can schedule an unstamped worker-local start; that experiment failed closed and remains unqualified for browser/facade parity. No epoch exception was introduced. The new idle deadline is required only when formulas or replica/cache applications remain; removing the last formula retains the existing no-result completion behavior.

Final corrective qualification: all 39 affected cases passed across the real RPC, formula display and worker-boundary suites; full workspace typecheck and guard passed. Earlier failed logs were retained: the first strict comparison missed source-preservation normalization, and the first generic start deadline incorrectly waited for a graph after the last formula was removed. Both were corrected in the owning code without relaxing their tests. No package, renderer, browser UI, server-history asset or release qualification is claimed by this checkpoint.

## Ordinary calculation and Save

The Grid's actual Save binding uses the quiescent wait, not the narrower replica-only membership wait. Published calculation state remains pending while an owned generation or cache application is outstanding, including ordinary edits and explicit host calculation starts. Worker failure republishes stored/unavailable status and refuses the wait; it does not silently mark the workbook live.

A genuine regression against `a061c9b5` held the real reverse cache application after an ordinary edit: the raw cache remained 38 while status incorrectly reported live. The corrected test requires pending status until actual cache 40 is applied. A separate private clean-resume development test also holds this packet across a Save request and checks transport timing; that test and its qualification belong to the later consumer checkpoint, not this isolated delta. Pending save identity/snapshot immutability is unchanged; final XLSX calculation and source authority remain owned by the existing contained pipeline.

Save-gate follow-up checks: 29 unchanged worker/RPC cases passed with `--maxWorkers=1`; the 11 display-policy cases had passed in the earlier combined run. That earlier run's worker startup/test-deadline failures are retained rather than called a full parallel pass. Full workspace typecheck and guard passed. The 5-second startup/execution bounds and all assertions stayed unchanged; concurrent local checking and pressure measurements support a contention hypothesis without proving its cause. These remain local source tests, not packaged or production acceptance.
